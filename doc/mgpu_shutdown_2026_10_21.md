# MG-10: завершение прохода без бесконечного ожидания

21.10.2026. Исправление к `0395a66b`, поверх обновления документации Андрея `39a56d18`.

## Причина

Прежний деструктор повторял `reset()` до успеха. Если очередь GPU ждала внешний fence,
который никогда не сигналится, каждая попытка завершалась тайм-аутом и цикл продолжался бесконечно.
Простой выход из цикла был бы ошибкой: поля прохода освободили бы ресурсы и вернули память в пул
раньше завершения GPU.

## Исправление

Все объекты выполнения вынесены в `DeviceFullscreenPass::State`. Деструктор вызывает `reset(0)`
один раз. Если завершение ещё не подтверждено, он передаёт State в список отложенного освобождения
и возвращается. Передача не выделяет дополнительную память: State создан при `init()`, ссылка списка
встроена в него.

State сохраняет очередь, command allocator/list, PSO, root signature, descriptor heap, ресурсы,
их mapped upload-память, completion fence/event, ожидаемые внешние fence и shared-владение аллокатором.
Поэтому исчезновение исходного владельца аллокатора не оставляет висячий указатель в `DeviceResource`.

`collectRetiredResources()` обходит весь список без ожидания. Он освобождает только State,
для которого завершился собственный fence или подтверждено удаление устройства. Незавершённая запись
не мешает освобождению других записей. Метод возвращает число оставшихся State.
Фоновые потоки и их ожидание при выходе не создаются; статические деструкторы не освобождают
память незавершённых команд.

`reset(timeout)` остаётся явной операцией завершения с HRESULT. Тайм-аут сохраняет проход для повторной
попытки или обработки отказа владельцем. `reset(0)` теперь только проверяет значение fence:
повторные проверки не создают новые регистрации `SetEventOnCompletion` для зависшей очереди.
Продюсер не сигналит fence потребителя искусственно и не вызывает `RemoveDevice()` из деструктора.

## Контракт интеграции

`DeviceFullscreenPassDesc::allocator` теперь имеет тип `eastl::shared_ptr<IDeviceResourceAllocator>`.
Нужно передать настоящую shared-ссылку, а не обёртку над стековым объектом с пустым deleter:

```cpp
eastl::shared_ptr<NauDeviceResourceAllocator> allocator = eastl::make_shared<NauDeviceResourceAllocator>();
const HRESULT result = allocator->init(secondaryDevice);
// Проверить result, затем передать allocator в desc.allocator и вызвать pass.init(desc).
```

Все вызовы, включая сбор отложенных объектов, по-прежнему выполняются последовательно в потоке рендера.
`init()` и `execute()` автоматически вызывают сбор. При интеграции в основной кадр надо также вызывать
`DeviceFullscreenPass::collectRetiredResources()` раз в кадр и при завершении, пока модуль Render
и код аллокатора ещё загружены. Не нужно крутить бесконечный цикл до нулевого результата.

Нормальное завершение: прекратить новые отправки, разрешить зависимости потребителей, вызвать
`pass.reset(timeout)`, проверить HRESULT, собрать завершённые отложенные объекты и завершить аллокатор.
При ошибке владелец прекращает использование вторичного пути и выполняет предусмотренное восстановление.
Внешний fence удерживается проходом до завершения соответствующего GPU-ожидания.
Если target читает другая очередь, её release fence надо зарегистрировать через `waitForExternalWork()`
перед перезаписью, reset или уничтожением прохода. Автоматически обнаружить незарегистрированного
внешнего потребителя по обычному native-указателю невозможно.

Если зависимость никогда не завершится и устройство останется живым, её память останется закреплённой
до завершения процесса. Это осознанное аварийное удержание ресурсов, позволяющее избежать use-after-free
и зависания выхода. Это не исправляет саму потерянную синхронизацию. Нельзя бесконечно создавать новые
проходы вместо зависших; владелец должен обработать отказ. Выгрузка Render при незавершённой работе
также не является корректным способом освобождения GPU-памяти.

## Регрессионные проверки

- `DestructorRetiresBlockedWorkAndKeepsAllocatorAlive`: очередь ждёт несигналенный fence; исходный
  владелец аллокатора исчезает; деструктор возвращается быстрее 1 секунды, три выделения остаются живы.
  После настоящего сигнала потребителя сбор освобождает State и аллокатор. Запускается на WARP и hardware.
- `RetirementCollectsCompletedWorkBehindBlockedEntry`: две отложенные записи; зависшая находится в голове.
  Вторая освобождается независимо, первая сохраняет три выделения до своего сигнала. WARP и hardware.
- `ProcessExitsWithPermanentlyUnsignaledExternalFence`: отдельный процесс с WARP никогда не сигналит
  fence и возвращается из `main` обычным путём. Родитель проверяет завершение за 10 секунд.
  При регрессии родитель останавливает только свой тестовый процесс и сообщает ошибку.
- Существующие проверки отрисовки, readback, владения, тайм-аутов и debug layer остаются в наборе.
  Тесты после разрешения зависимостей проверяют отсутствие оставшихся resource/heap.

В отдельном тесте постоянного зависания память намеренно удерживается до выхода процесса;
его критерий — нормальное завершение процесса, а не нулевое число живых GPU-объектов до выхода.
